## 2. Normative Precedence & Hierarchy Rules

When reading specifications, requirements, architecture decisions, or ticket history, apply authority by artifact type:

1. **Ratified local ADRs** govern settled architectural decisions.
2. **Canonical local specs** govern behavior, contracts, and requirements.
3. **`feature_list.json`** governs lifecycle/acceptance status and verification claims; it does not erase stale spec metadata.
4. **Local ticket files** govern current planning, research, and wayfinding.
5. **GitHub issues** are historical provenance and migration evidence; they are never silently promoted over a local source.

- **Semantic Drift Resolution**: If text in an earlier GitHub issue or draft spec contradicts a ratified ADR or accepted `feature_list.json` entry, the local committed document strictly prevails.
- **Explicit Conflict Recording**: Any semantic discrepancy must be recorded in the Conflict Register with both sources and the normative resolution; it must never be silently overwritten or ignored.

- **Normative Resolution**: `feature_list.json` remains the normative lifecycle authority, and the local F060 spec metadata has been synchronized to the same accepted state without changing the normative content. Conflict Register `CR-001` is resolved.

- **Normative Rule**: IDs `0001–0006` are permanently reserved identifiers (not present files). They must never be reused or backfilled. Recorded in Uncertainty Register `UR-001`.

- **Normative Rule**: Classify `#76–#84` as `historical-provenance`, retain the registry omission as an intentional historical-only disposition, and do not invent feature-registry entries during this reconciliation. F015/F016 remain independent canonical features; any future backfill must be a separate governed change with its own evidence. Recorded in Uncertainty Register `UR-004`.
