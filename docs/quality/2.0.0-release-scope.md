## 1. What this certifies, and what it does not

**It certifies:** which work belongs to the 2.0.0 release, and where the evidence for each
item in that scope lives (feature registry status, canonical spec, recorded evidence count,
and how often the history cites it).

**It does not certify:** that every requirement of every canonical spec has been
independently verified. Nothing here re-reads a spec clause by clause; it maps scope to
evidence and names the gaps. Treating this document as "all specs complete" would be a
claim it does not make.

## 3. The scope rule

A requirement is **in scope** for 2.0.0 when its work landed in `v1.6.0..HEAD`. Everything
else is **out**, and named here so "out" is a decision rather than an omission:

- `docs/specs/trusted-control-evolution.md` is `proposed` — explicitly pending coordinator
  re-review, implementation not started. Out of scope.
- Platform limits stated by a shipped spec are out of scope as work items: F081's macOS
  process-identity probe is implemented but unverified (no macOS host was available), and
  Windows process identity is deliberately not implemented (its only primitive is a process
  spawn, measured at 1-3s per call). Both are recorded in the spec, not silently absent.

## 5. Gaps this reconciliation exposes

1. **2 ids are cited by the history but absent from the registry** (F013, F014). They are not claims of delivered work — the range mentions them in passing — but the
   registry is the authoritative list of features, so a reader cannot resolve them there.
2. **16 features are `passing`, not `accepted`** (F066, F067, F068, F069, F070, F071, F072, F073, F074, F075, F076, F077, F078, F079, F080, F082).
   `passing` means implemented with recorded evidence (the validator refuses `passing`
   without evidence); `accepted` is the stronger state that a human acceptance Decision
   produces. This release ships them as tested, not as human-accepted.

   **Audited, and deliberately left as `passing`.** Every one of the 16 was run through the
   acceptance gate read-only: **0 of 16 are acceptance-ready**. Each is blocked by 9-10
   errors of ONE family — the plans predate the current plan template, so the gate cannot
   find `## High Level Design`, `## Vertical Slices`, `## Resume Checkpoint`,
   `## Acceptance Criteria` (with a phase-boundary acknowledgment), the `## Context
   manifests` implement/review roles, a confirmed `User Confirmation`, or in 9 cases a
   `## Verification` section. Turning them into `accepted` therefore means rewriting 16
   already-delivered plans to the current template AND taking 16 separate human decisions —
   high churn for a status, and `passing` is already an evidence-backed state that this
   document certifies as such. If the project wants them accepted, the cheapest path is to
   regenerate each plan from the current template (`amber plan`) and accept per feature; that
   is a governance decision, not a step taken here.
3. **28 of 61 in-range features have no canonical spec** (F001, F007, F013, F014, F022, F023, F024, F025, F026, F027, F031, F033, F034, F035, F036, F037, F038, F039, F040, F041, F042, F043, F044, F045, F046, F047, F048, F082).
   A spec is required for the harness/contract surfaces, not for every feature; this is
   stated so the absence is not read as a missing document.
4. **Plan headers now agree with the registry.** The 16 legacy plans (F065-F080) recorded
   `implementation-ready` while their features were already delivered; each header now states
   the registry value and preserves the original sentence as history. One contradiction stays
   visible rather than smoothed over: F065's header still records *"user confirmation pending
   in issues/0069"* while the registry says `accepted`.
5. **The plan gates only read one header style until this release.** `readPlanField` matched a
   plain `Status:` line, so the 16 bold-headed plans (`**Status:**`) were invisible to
   `review`/`accept`. Both styles are read now, and `accept` rewrites the bold line in place.
6. **The canonical specs are mostly not in an accepted state** — the release report's phrase
   "proposed/draft states and metadata drift", quantified: of 45 specs, 16 are `accepted` and
   1 `Accepted (2026-08-30)`, while 14 are `Proposed`, 4 `proposed`, 3 `draft`, 1 `draft-v1`,
   1 `Reconciliation required`, and **5 carry no Status line at all** (including
   `sync-envelope-contract.md`, a shipped surface). The drift is also one of convention:
   `accepted`/`Accepted` and `Proposed`/`proposed` are written both ways. State alone does
   not establish an implementation gap — the report says so, and this document does not
   claim otherwise — but a reader cannot tell a delivered spec from a planned one without
   opening it. Worth a documented status vocabulary and a gate; not assumed here.
