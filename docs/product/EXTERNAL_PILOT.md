# 外部试点协议（External Pilot Protocol）

**Status:** 协议就绪；**试点未开始**（外部阻塞：需要一个真实参与的仓/团队）
**Owner:** 主用户任命；Amber 侧只提供协议与工具，不代跑
**账本:** `docs/quality/continuation-log.md`（外部仓行单独记账）
**相关:** `docs/product/LOOP.md`、`docs/agents/dev-workflow.md`、ADR-0030（F082 定位修正案）

---

## 1. 为什么需要它

仓库内能自证的东西已经自证完了：全量门禁、双轴评审、机制化的 parity 检查、50 个本地提交。
这些都只证明**代码是对的**。它们不证明**这个边界在别人的仓库里有用**。

定位已按 §55 翻到 first screen（ADR-0030 F082 修正案，以内仓证据替代外部信号——那是一次显式的
scope override）。因此外部试点的作用不再是「解锁定位」，而是**检验定位这句话是否成立**：

> 一个已经在用 coding agent 做真实交付的团队，换成 Amber 治理后，
> 下一个人/agent 能否不读旧聊天就正确接续？

这个问题只有外部仓能回答。内仓 dogfood 是必要条件，不是充分条件。

## 2. 试点不是什么

- **不是 demo**：跑通 `init` → `doctor` → `handoff` 不算结果。文件生成不是激活。
- **不是访谈**：「感觉有用」不进分子。
- **不是我们代跑**：Amber 侧不进入对方仓库、不代为提交、不接触对方聊天记录。
- **不是定位投票**：定位已定；试点产出的是缺口清单，不是「要不要翻」的重议。

## 3. 入选条件

一个仓同时满足：

1. **真实交付**：该仓已经持续使用一个或多个 coding agent 做真实工作（不是试用、不是玩具仓）；
2. **人类担责**：有具名的人类审查者/维护者承担审查责任；
3. **两个角色**：至少能提供「交付者」与「后继者」两个不同的人/会话——后继者不得是写出该 handoff 的同一会话（账本头规则）；
4. **一个真实任务**：选一个正在进行中的任务，不为试点造任务；
5. **同意记账**：允许把**脱敏后的判定结果**（不是源码、不是聊天）记进公开账本的外部区。

## 4. 流程（一轮 = 一行账本）

| 步 | 谁做 | 做什么 | 产出 |
| --- | --- | --- | --- |
| P0 | 主用户 | 确认入选条件、指定具名对接人 | 对接人 + 仓标识（可脱敏） |
| P1 | 对方团队 | 装 Amber，`amber init` / `doctor`，跑一次 `audit` | 对方自己留有 install 记录 |
| P2 | 对方交付者 | 用 Amber 走**一个真实任务**（plan → gate → 实现 → 证据），需要时 `session start/stop` | 仓内 plan / 证据 / feature 状态 |
| P3 | 对方交付者 | `amber handoff` 生成交接包 | `session-handoff.md` |
| P4 | 对方后继者 | **盲读**：只允许读交接包（禁读任何聊天、禁问交付者） | 四问作答 |
| P5 | 对方后继者 | 实际执行**一条可核验的只读下一步动作**（T5 起的账本规则） | 命令 + 输出 |
| P6 | 独立判定人 | 对照地面真值（git 事实、仓内文件）逐格判定 | 四格结果 + 缺失工件 |
| P7 | 主用户 | 把该行（脱敏）写进 `docs/quality/continuation-log.md` 外部区 | 账本行 |

### 四问（唯一评分口径）

| 格 | 问题 | 地面真值来源 |
| --- | --- | --- |
| ① | 改了什么？ | `git log` / feature 状态 / 仓内文件 |
| ② | 谁批准？ | 审批/确认记录是否在包内可读 |
| ③ | 证据在哪？ | 命令可复跑 + 日志/工件路径真实存在 |
| ④ | 下一步？ | 建议的动作是否成立（不成立即失败，即使措辞自信） |

每格只有对/半对/错；**不读旧聊天仍能作答**是前提，不是加分项。

## 5. 验收口径（服从账本，不自定一套）

测量口径的权威在 `docs/quality/continuation-log.md`，本协议**不另立阈值**。当前相关条款：

| 口径 | 来源 | 内容 |
| --- | --- | --- |
| 季末外部验收 | 账本「本季验收（至 2026-12-22）」 | 二者其一：①「未验证」——外部独立仓真实续接尝试仍为 0；②「第一个外部仓」——非本仓、非维护者日常开发仓完成 J0 → doctor 可复验 → **≥ 3 次已判定的真实 J2 尝试** |
| 四问评分 | 账本头 | 每格对/半对/错；禁读旧聊天是前提不是加分项 |
| 判定人 | 账本头 | 不得是刚写出该 handoff 的同一会话 |
| 禁入分子 | 账本头 | `init` 次数、命令退出码、文件存在性、session 计数 |
| 失败具名 | 账本头 + T0/T1 先例 | 非满分格必须点出缺失工件名 |

试点期间外部行记进账本的「外部仓记录」区（与 dogfood 分开）。若主用户想给外部行另加通过率门槛，那是账本条款修订（需改账本），不是本协议能宣布的事。

## 6. 失败如何处置

试点失败**是结果**，不是事故。按内仓既有做法处理：

1. 每条失败转成**具名产品缺口**（内仓 T0/T1 的写法：`next` 验收态短路、handoff 无审批维度、会话摘要滞后……）；
2. 缺口进 `issues/` 单独成票，**不在试点票里顺手修**；
3. 试点报告同时写「通过几轮」与「缺口几条」——只报通过率的报告视为不合格。

## 7. 边界（试点期间不放松）

- 证据只落对方仓内 + `.amber/`；Amber 不写对方仓以外的系统；
- 不采集对方源码、聊天、凭据；账本只记脱敏判定结果；
- 不承诺替代对方引擎/CI/评审；试点只加治理与证据，不换工具链；
- 对方随时可退出，退出前的行保留（账本是事实，不是评分表）。

## 8. 出口：用结果做什么决策

试点结束后，按账本「本季验收」条款先定性（「未验证」还是「第一个外部仓」），再由主用户据以下三项之一裁决（一次一个）：

1. **继续扩面**：阈值达到 → 讨论分发/文档/集成面（另开 scope）；
2. **先补缺口**：通过率不足但失败模式集中 → 按缺口批量修复后再跑一轮；
3. **调整定位叙事**：失败模式指向「这不是买家关心的问题」→ 回看 §55 首屏措辞（ADR-0030 可再修正）。
